# AGENTS.md

This file tells coding agents and human contributors how to work safely and effectively in this repository.

## Project overview

Pi Coding Agent for VS Code is a dedicated VS Code interface for the real [Pi coding agent](https://pi.dev). It is not a second agent implementation and it is not a wrapper around VS Code Copilot.

The extension launches `pi --mode rpc` as a workspace-sidecar process, translates Pi's JSONL RPC events into a VS Code webview, and sends user actions back through Pi's documented RPC protocol. Pi remains responsible for models, credentials, tools, extensions, skills, prompt templates, sessions, MCP, compaction, retries, and agent behavior.

Current product status and future work are tracked in [GAMEPLAN.md](GAMEPLAN.md).

## Non-negotiable architecture rules

1. **Keep Pi authoritative.** Do not reimplement Pi's agent loop, model registry, tool execution, session format, package manager, or MCP orchestration in the extension.
2. **Prefer RPC and supported CLI commands.** Use `pi --mode rpc` for live sessions and supported Pi CLI commands for package/runtime operations.
3. **Treat existing Pi configuration as canonical.** Respect `PI_CODING_AGENT_DIR`, `PI_CODING_AGENT_SESSION_DIR`, `~/.pi/agent`, project `.pi` resources, and Pi's own settings.
4. **Use stable VS Code APIs.** Do not require proposed chat or MCP APIs for core behavior.
5. **Do not expose secrets to the webview.** Credentials stay in Pi's credential store. Never log, render, persist, or test with real API keys or OAuth tokens.
6. **Preserve user work.** Change review must restore the exact pre-task working-tree state, including dirty and untracked files that existed before Pi ran. Never equate “before Pi” with `HEAD`.
7. **Bound all context and output.** Session parsing, diagnostics, terminal metadata, file content, tool output, and bridge responses need explicit size limits.
8. **Keep context user-directed.** Prefer `@mentions` and explicit slash commands over registering a large autonomous VS Code tool surface.
9. **No uncontrolled concurrent writers.** Future multi-session and subagent work must use a workspace write lease or isolated Git worktrees.
10. **Honor Workspace Trust.** Project-local Pi resources may execute instructions. Never silently approve an untrusted workspace.

## Repository layout

```text
pi-vscode/
├── src/
│   ├── extension.ts          # VS Code activation and command registration
│   ├── piViewProvider.ts     # Current host controller and webview HTML
│   ├── piRpcClient.ts        # Pi process lifecycle and JSONL RPC transport
│   ├── jsonl.ts              # Incremental JSONL decoder
│   ├── contextMentions.ts    # @context parsing and bounded payload helpers
│   ├── changeReview.ts       # Git object checkpoints, diffs, accept/revert
│   └── sessionLibrary.ts     # Pi JSONL session discovery and metadata parsing
├── pi-bridge/
│   └── index.ts              # Pi extension bridge for MCP status events
├── webview/
│   └── main.js               # Webview source; edit this, not the generated bundle
├── media/
│   ├── main.css              # Webview styles
│   └── main.js               # Generated and tracked webview bundle
├── test/                     # Vitest unit, integration, and DOM tests
├── assets/                   # Extension icon assets
├── package.json              # Extension manifest and scripts
├── README.md                 # Human-facing project documentation
└── GAMEPLAN.md               # Completed work and forward roadmap
```

`dist/` and VSIX files are generated and ignored. `media/main.js` is generated by esbuild but intentionally packaged and tracked; never edit it by hand.

## Development setup

Requirements:

- Node.js 22 or newer is recommended.
- VS Code 1.100 or newer.
- Pi installed and configured on the development machine.

Install dependencies and validate the repository:

```bash
npm install
npm run check
```

Launch an Extension Development Host with `F5` in VS Code.

Build a VSIX:

```bash
npm run package
```

Install the result locally:

```bash
code --install-extension pi-vscode-<version>.vsix --force
```

Reload VS Code after installing a new local build.

## Standard workflow

Before editing:

```bash
git status --short --branch
git log -3 --oneline
```

Use a focused feature branch or worktree for substantial work. Do not mix refactors, generated-file churn, and unrelated features in one commit.

After editing:

```bash
npm run check
git diff --check
git status --short
```

For changes to runtime startup, RPC handling, Pi bridge behavior, sessions, or packaging, also perform a real Pi smoke test and verify the built VSIX contains the expected files.

## Build and test commands

```bash
npm run clean          # remove dist/
npm run compile        # TypeScript + webview bundle
npm run build:webview  # regenerate media/main.js
npm test               # Vitest suite
npm run check          # compile and test
npm run package        # check and produce a VSIX
```

### Test responsibilities

- `test/jsonl.test.ts`: chunked and malformed JSONL transport behavior.
- `test/contextMentions.test.ts`: mention parsing and context extraction.
- `test/changeReview.test.ts`: dirty-tree checkpoint and exact file restoration behavior.
- `test/sessionLibrary.test.ts`: JSONL metadata parsing and archive behavior.
- `test/webviewBundle.test.ts`: browser-side rendering and message handling in JSDOM.

When adding a subsystem, add focused tests instead of extending only the broad webview test.

## Coding conventions

### TypeScript and extension host

- Keep TypeScript strict and avoid `any` unless adapting an untyped external protocol boundary.
- Validate all data crossing RPC or webview boundaries. Treat it as untrusted input.
- Use `vscode.Uri` and `vscode.workspace.fs` when VS Code resource semantics matter.
- Keep filesystem and Git operations outside the webview.
- Log operational diagnostics to the `Pi Coding Agent` output channel without including prompt contents or credentials unless explicitly needed for debugging.
- Prefer capability checks over hard-coded Pi version checks.
- Keep shutdown idempotent; processes must be terminated when views, runtimes, or the extension are disposed.

### Pi RPC

- Pi writes one JSON object per line. Preserve strict line framing.
- Every request must have a unique ID and a bounded timeout.
- Handle process exit by rejecting pending requests.
- Do not infer agent state solely from rendered messages; use RPC state/events.
- Preserve Pi extension UI requests and return responses through the proper RPC channel.
- When adding a new Pi API dependency, consult the installed Pi documentation and add a real runtime smoke test.

### Webview

- Edit `webview/main.js`; `npm run build:webview` regenerates `media/main.js`.
- Keep the Content Security Policy restrictive.
- Render Markdown through the existing sanitizer. Never inject model, tool, session, MCP, or filesystem text directly as trusted HTML.
- Use `textContent` for ordinary dynamic content.
- Include keyboard and accessible-name behavior for new controls.
- Update both host and webview protocol handling together.
- Add JSDOM coverage for new message types and interactive components.

### Git change review

- Checkpoints use temporary Git indexes and refs under `refs/pi-vscode/checkpoints/`.
- Never mutate the user's real index while capturing a checkpoint.
- Revert restores the captured pre-task tree, not repository `HEAD`.
- “Accept” means “keep and mark reviewed”; it does not stage or commit the file.
- Cover tracked, staged, dirty, untracked, deleted, binary, and renamed files when changing this subsystem.

### Sessions

- Pi JSONL files are the source of truth.
- Session discovery must respect custom Pi agent/session directories.
- Do not rewrite JSONL session files directly for operations Pi supports through RPC.
- Archive operations must be reversible; destructive deletion requires explicit confirmation and should use the operating-system trash when available.
- Parsing must tolerate malformed, partial, old, and actively-written JSONL files.

### MCP

- The installed `pi-mcp-adapter` owns MCP execution and configuration semantics.
- The VS Code extension consumes adapter status and invokes supported adapter commands; do not create a second MCP client stack.
- OAuth and approval interactions must flow through Pi's extension UI/RPC behavior.

## Security checklist

Before merging a feature, ask:

- Does it execute a command or modify a file without clear user intent?
- Could project-local resources influence it in an untrusted workspace?
- Could sensitive prompt, session, environment, or credential data reach the webview or logs?
- Are paths normalized and restricted to the intended workspace/resource scope?
- Is external content sanitized and size-limited?
- Can cancellation terminate every child process?
- Does failure preserve existing user files and Git state?

Future package installation, editor mutation, multi-session writing, and subagents require explicit security review.

## Release checklist

1. Update `package.json` and `package-lock.json` versions together.
2. Update `README.md` and `GAMEPLAN.md` for user-visible behavior.
3. Run `npm run check`.
4. Run `git diff --check`.
5. Package with `npm run package`.
6. Inspect VSIX contents; ensure `dist/src`, `media`, assets, and `pi-bridge/index.ts` are present.
7. Install the VSIX with `--force`.
8. Reload VS Code and run a live chat/tool/MCP smoke test.
9. Commit source and generated `media/main.js` together.
